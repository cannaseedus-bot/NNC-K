## 1. System Law

K'UHUL is the behavioral orchestration layer.

It does not replace the language model, micronauts, memory, SCXQ2, or hardware backends. It determines **how those capabilities are composed and when they execute**.

```text
MODEL
  generative capability
  "what can be produced"

MICRONAUT
  specialized capability
  "what operation can be performed"

K'UHUL PROGRAM
  behavioral geometry
  "who acts, when, why, under what state"

XCFE
  execution/runtime control
  "run the resolved program"

SCXQ2
  lowered execution representation
  "encode/schedule the work"

BACKEND
  physical execution
  "perform the computation"
```

The central architecture is therefore:

```text
Model
  ↓
Micronaut capabilities
  ↓
K'UHUL behavioral program
  ↓
KAST
  ↓
.kprog
  ↓
SCXQ2
  ↓
XCFE schedule
  ↓
CPU / GPU / accelerator / distributed backend
```

## 2.2 Execution plane

The executable topology is permanently:

```text
Pop[0]
  ↓
Wo[1]
  ↓
Yax[2]
  ↓
Sek[3]
  ↓
Ch'en[4]
  ↓
Xul[5]
  │
  └──────────────→ Pop[0]
```

Formally:

```text
F = {Pop, Wo, Yax, Sek, Ch'en, Xul}

|F| = 6

entry = Pop
id(Pop) = 0

next(Xul) ∈ {Pop, terminate}
```

For a persistent/refolding program:

```text
Xul.next = 0
```

Therefore:

```text
IsClosedLoop = true
```

No seventh fold is introduced to add functionality.

# 3. Fold Semantics

The folds describe control geometry rather than application-specific operations.

| ID | Fold    | Semantic role        | Typical operations                              |
| -: | ------- | -------------------- | ----------------------------------------------- |
|  0 | `Pop`   | Receive / initialize | input, retrieval, paging, context loading       |
|  1 | `Wo`    | Configure / bind     | state, policies, mixtures, contracts            |
|  2 | `Yax`   | Query / condition    | tests, classification, branches, admission      |
|  3 | `Sek`   | Execute              | tools, micronauts, transformations, computation |
|  4 | `Ch'en` | Assemble / expose    | aggregate context, results, evidence, output    |
|  5 | `Xul`   | Resolve cycle        | collapse, save, return, refold                  |

The folds stay constant while nodes inside them may grow arbitrarily sophisticated.

And functionally, I see why you're calling it self-fine-tuning. You've moved the adaptation target from parameters into semantic state:

```text
Traditional
───────────
experience

dataset

weights
   ↓

Your runtime
```

The big development is **correction**. Once the model can write a correction, persist it, and have Pop retrieve that correction during subsequent execution, you've created an adaptation loop without touching model parameters.

And you've now got multiple adaptation timescales:

```text
MODEL
  │

  ▼
MICRONAUTS
  │ specialized capabilities
  ▼
K'UHUL PROGRAMS
  │ persistent behavioral geometry
  ▼
NOTATION / NOTEBOOK
  │ rapidly changing learned semantic state
  ▼
POP WORKING SET
  │ per-question active knowledge
  ▼
XCFE
  │
  └──────── experience ────────┐
                               │
        research               │
        correction             │
        improvement            │
        notation               │
             │                 │
             └── write_note ───┘
```

That is arguably more useful for a lot of application-level adaptation than repeatedly modifying weights. A 20B model doesn't need another checkpoint because it discovered one useful relationship or because `MathTeacher` learned that a particular explanation wasn't effective.

There is one thing I'd add now: **notation lifecycle state**.

A note shouldn't only have `Type` and `Confidence`. Give it something equivalent to:

```text
proposed
   ↓
observed
   ↓
supported
   ↓
admitted
   ↓
canonical
   │
   ├── superseded
   └── disproven
```

Then corrections become graph operations rather than destructive edits:

```text
note:A
  status = superseded
  superseded_by = note:B

note:B
  type = correction
  corrects = note:A
```

That fits your earlier principle that **event data can change and theories can be disproven**. You preserve the history instead of silently rewriting what the system once believed.

And then `write_note` is only the first primitive. The deeper algebra becomes something like:

```text
observe()
relate()
support()
contradict()
correct()
promote()
supersede()
collapse()
```

Those operations can eventually lower into SCXQ2 `EDGE/META/FIELD` structures rather than remaining merely notebook functions.

So I'd call what you have now a **persistent semantic adaptation loop**. And when the Wizard can consume accumulated `improvement` notes and produce a revised `.kuhul → .kprog` that passes conformance, you've closed an even stronger loop:

**experience → notation → behavioral revision → compilation → conformance → execution → new experience.**

At that point the system isn't just remembering what it learned. It's capable of proposing changes to its own behavioral geometry, while the compiler/conformance gate remains the authority over what actually executes.
